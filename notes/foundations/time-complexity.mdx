# Time Complexity

If [Asymptotic Analysis](../asymptotic-analysis/) gave you the language of growth rates, this note is about **applying it fast when reading or writing code**: recognizing complexity patterns at a glance, using problem constraints to pick an approach, and knowing the costs of the building blocks you reach for.

## Reading Complexity from Code

Given unfamiliar code, you can usually read off the time complexity directly from its control flow.

### $O(1)$ — Direct access or closed-form formula

No loops, no recursion, no input-dependent work:

```python
arr[i]
d[key]
(n * (n + 1)) // 2   # closed-form formula
```
```julia
arr[i]
d[key]
n * (n + 1) ÷ 2      # closed-form formula
```
```ts
arr[i];
map.get(key);
(n * (n + 1)) / 2;   // closed-form formula
```
```rust
arr[i];
map[&key];           // or map.get(&key) if the key may be missing
n * (n + 1) / 2;     // closed-form formula
```

### $O(\log n)$ — Halving or doubling

The remaining work is cut (or grown) by a constant factor on every step:

```python
# Halving
i = n
while i > 0:
    i //= 2          # log₂n iterations

# Binary search
lo, hi = 0, len(arr) - 1
while lo <= hi:
    mid = (lo + hi) // 2
    ...
```
```julia
# Halving
i = n
while i > 0
    i ÷= 2          # log₂n iterations
end

# Binary search
lo, hi = 1, length(arr)
while lo <= hi
    mid = (lo + hi) ÷ 2
    # ...
end
```
```ts
// Halving
let i = n;
while (i > 0) {
  i = Math.floor(i / 2);   // log₂n iterations
}

// Binary search
let lo = 0;
let hi = arr.length - 1;
while (lo <= hi) {
  const mid = Math.floor((lo + hi) / 2);
  // ...
}
```
```rust
// Halving
let mut i = n;
while i > 0 {
    i /= 2;         // log₂n iterations
}

// Binary search (hi is exclusive, so it never underflows)
let (mut lo, mut hi) = (0, arr.len());
while lo < hi {
    let mid = lo + (hi - lo) / 2;
    // ...
}
```

Whenever you see a value halved, doubled, or split at a midpoint, think $O(\log n)$.

### $O(n)$ — Single pass

One loop (or two pointers moving monotonically), constant work per step:

```python
total = 0
for x in arr:
    total += x
```
```julia
total = 0
for x in arr
    total += x
end
```
```ts
let total = 0;
for (const x of arr) {
  total += x;
}
```
```rust
let mut total = 0;
for &x in &arr {
    total += x;
}
```

Also includes building a hash map from an array, linear scans, prefix sums, and sliding windows.

### $O(n \log n)$ — Sort, or divide-and-conquer with linear merge

Either an explicit sort, or splitting into halves ($\log n$ levels) while doing $O(n)$ total work at each level:

```python
arr.sort()           # O(n log n)

def merge_sort(arr):
    if len(arr) <= 1:
        return arr
    mid = len(arr) // 2
    left = merge_sort(arr[:mid])    # T(n/2)
    right = merge_sort(arr[mid:])   # T(n/2)
    return merge(left, right)       # O(n)
```
```julia
sort!(arr)           # O(n log n)

# merge_sorted, not merge: Base.merge already exists (for dictionaries)
function merge_sort(arr)
    if length(arr) <= 1
        return arr
    end
    mid = length(arr) ÷ 2
    left = merge_sort(arr[1:mid])       # T(n/2)
    right = merge_sort(arr[mid+1:end])  # T(n/2)
    return merge_sorted(left, right)    # O(n)
end
```
```ts
arr.sort((a, b) => a - b);   // O(n log n). Without a comparator, sort() compares as strings

function mergeSort(arr: number[]): number[] {
  if (arr.length <= 1) {
    return arr;
  }
  const mid = Math.floor(arr.length / 2);
  const left = mergeSort(arr.slice(0, mid));   // T(n/2)
  const right = mergeSort(arr.slice(mid));     // T(n/2)
  return merge(left, right);                   // O(n)
}
```
```rust
arr.sort();          // O(n log n)

fn merge_sort(arr: &[i32]) -> Vec<i32> {
    if arr.len() <= 1 {
        return arr.to_vec();
    }
    let mid = arr.len() / 2;
    let left = merge_sort(&arr[..mid]);    // T(n/2) — borrows, no copy
    let right = merge_sort(&arr[mid..]);   // T(n/2)
    merge(&left, &right)                   // O(n)
}
```

### $O(n^2)$ — Nested loops (and hidden linear calls inside loops)

```python
for i in range(n):
    for j in range(i, n):   # triangle: n(n+1)/2 = O(n²)
        ...

# Hidden O(n²) — membership check on a list is O(n)
for x in arr:
    if x in another_arr:    # convert another_arr to a set first!
        ...
```
```julia
for i in 1:n
    for j in i:n            # triangle: n(n+1)/2 = O(n²)
        # ...
    end
end

# Hidden O(n²) — `in` on a Vector is O(n)
for x in arr
    if x in another_arr     # convert another_arr to a Set first!
        # ...
    end
end
```
```ts
for (let i = 0; i < n; i++) {
  for (let j = i; j < n; j++) {   // triangle: n(n+1)/2 = O(n²)
    // ...
  }
}

// Hidden O(n²) — includes() on an array is O(n)
for (const x of arr) {
  if (anotherArr.includes(x)) {   // convert anotherArr to a Set first!
    // ...
  }
}
```
```rust
for i in 0..n {
    for j in i..n {               // triangle: n(n+1)/2 = O(n²)
        // ...
    }
}

// Hidden O(n²) — contains() on a Vec/slice is O(n)
for x in &arr {
    if another_arr.contains(x) {  // convert another_arr to a HashSet first!
        // ...
    }
}
```

### $O(2^n)$ — Branching recursion or subsets

Each step branches into two (or more) subproblems of size $n - 1$, doubling the work at each level:

```python
def f(n):
    if n == 0:
        return
    f(n - 1)    # branch 1
    f(n - 1)    # branch 2
```
```julia
function f(n)
    n == 0 && return
    f(n - 1)    # branch 1
    f(n - 1)    # branch 2
end
```
```ts
function f(n: number): void {
  if (n === 0) return;
  f(n - 1);   // branch 1
  f(n - 1);   // branch 2
}
```
```rust
fn f(n: u32) {
    if n == 0 { return; }
    f(n - 1);   // branch 1
    f(n - 1);   // branch 2
}
```

## Reading Constraints to Pick an Approach

In interviews and coding assessments, the input constraint $n$ tells you what complexity class you need before you even design the algorithm. Assuming roughly $10^7$ simple operations per second:

| $n$ constraint | Target complexity | Typical techniques |
|----------------|-------------------|--------------------|
| $n \leq 12$ | $O(n!)$ or $O(2^n \cdot n)$ | Backtracking, permutation search |
| $n \leq 25$ | $O(2^n)$ | Subsets, bitmask DP, recursion with pruning |
| $n \leq 500$ | $O(n^3)$ | 3D DP, Floyd-Warshall, triple loop |
| $n \leq 5{,}000$ | $O(n^2)$ | 2D DP, all-pairs comparison |
| $n \leq 10^5$ | $O(n \log n)$ | Sorting, heaps, binary search per item, divide-and-conquer |
| $n \leq 10^6$ | $O(n)$ | Hash maps, two pointers, sliding window, prefix sums, monotonic stack |
| $n \leq 10^9$ | $O(\log n)$ or $O(\sqrt{n})$ | Binary search on answer, math, fast exponentiation |

### Common Optimization Moves

When your first brute-force idea is too slow for the constraints, reach for the matching move:

| Slow baseline | Target | Tool |
|---------------|--------|------|
| $O(n^2)$ lookup in a loop | $O(n)$ | Hash set / hash map |
| $O(n^2)$ checking all pairs | $O(n \log n)$ | Sort + two pointers |
| $O(2^n)$ overlapping recursion | $O(n)$ or $O(n^2)$ | Memoisation / dynamic programming |
| $O(n)$ per query on sorted data | $O(\log n)$ per query | Binary search |
| $O(n)$ per range-sum query | $O(1)$ per query | Prefix sums |
| $O(n)$ repeated min/max scan | $O(\log n)$ per update | Binary heap (priority queue) |

## Data Structure Operations

Every time you use a data structure inside a loop, its operation cost multiplies by the loop count.

| Structure | Access | Search | Insert | Delete | Space |
|-----------|--------|--------|--------|--------|-------|
| Array (static) | $O(1)$ | $O(n)$ | $O(n)$ | $O(n)$ | $O(n)$ |
| Dynamic array | $O(1)$ | $O(n)$ | $O(1)$† | $O(n)$ | $O(n)$ |
| Singly linked list | $O(n)$ | $O(n)$ | $O(1)$‡ | $O(1)$‡ | $O(n)$ |
| Deque (double-ended queue) | $O(n)$ | $O(n)$ | $O(1)$ ends | $O(1)$ ends | $O(n)$ |
| Hash table | — | $O(1)$* | $O(1)$* | $O(1)$* | $O(n)$ |
| Binary search tree | $O(\log n)$* | $O(\log n)$* | $O(\log n)$* | $O(\log n)$* | $O(n)$ |
| AVL / Red-Black tree | $O(\log n)$ | $O(\log n)$ | $O(\log n)$ | $O(\log n)$ | $O(n)$ |
| Binary heap | — | $O(n)$ | $O(\log n)$ | $O(\log n)$ | $O(n)$ |
| Trie | $O(k)$ | $O(k)$ | $O(k)$ | $O(k)$ | $O(n \cdot k)$ |

† Amortized at the end. ‡ Given a pointer to the node. \* Average case — worst case is $O(n)$ under hash collisions or an unbalanced BST. $k$ = key length.

> **Why arrays and linked lists have opposite trade-offs:** An array stores elements contiguously in memory, so jumping to index `i` is simple pointer arithmetic ($O(1)$), but inserting in the middle requires shifting every later element ($O(n)$). A linked list scatters nodes in memory, so rewiring a pointer to insert is $O(1)$, but reaching index `i` requires walking the chain from the head ($O(n)$).

For exact standard-library operation tables (`list.pop(0)`, `deque`, `Vec`, `HashMap`, `Map`/`Set`), see the dedicated language references:

- [TypeScript Big-O Cheatsheet](../typescript-big-o-cheatsheet/)

## Sorting Algorithms

| Algorithm | Best | Average | Worst | Space | Stable |
|-----------|------|---------|-------|-------|--------|
| Bubble sort | $O(n)$ | $O(n^2)$ | $O(n^2)$ | $O(1)$ | Yes |
| Selection sort | $O(n^2)$ | $O(n^2)$ | $O(n^2)$ | $O(1)$ | No |
| Insertion sort | $O(n)$ | $O(n^2)$ | $O(n^2)$ | $O(1)$ | Yes |
| Merge sort | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ | $O(n)$ | Yes |
| Quick sort | $O(n \log n)$ | $O(n \log n)$ | $O(n^2)$ | $O(\log n)$ | No |
| Heap sort | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ | $O(1)$ | No |
| Counting sort | $O(n + k)$ | $O(n + k)$ | $O(n + k)$ | $O(k)$ | Yes |
| Radix sort | $O(d(n + k))$ | $O(d(n + k))$ | $O(d(n + k))$ | $O(n + k)$ | Yes |
| Timsort (Python) | $O(n)$ | $O(n \log n)$ | $O(n \log n)$ | $O(n)$ | Yes |

$k$ = range of values, $d$ = number of digits.

**Key trade-offs:**
- **Merge sort** guarantees $O(n \log n)$ worst-case *and* stability, at the cost of $O(n)$ auxiliary space.
- **Quick sort** is fast in practice (cache-friendly, low overhead), but degrades to $O(n^2)$ on sorted input if you pick a naive pivot; randomising the pivot avoids this.
- **Insertion sort** runs in $O(n)$ on nearly-sorted data and has tiny constant factors — which is why hybrid sorts like Timsort use it on short runs ($< 64$ elements).
- **Counting / Radix sort** beat the $\Omega(n \log n)$ comparison lower bound by using integer digit structure instead of pairwise comparisons, assuming bounded key ranges.

## Graph Algorithms

| Algorithm | Time | Space | Use case |
|-----------|------|-------|----------|
| BFS | $O(V + E)$ | $O(V)$ | Shortest path (unweighted), level-order |
| DFS | $O(V + E)$ | $O(V)$ | Connectivity, cycle detection, topological sort |
| Dijkstra (binary heap) | $O((V + E) \log V)$ | $O(V)$ | Shortest path, non-negative weights |
| Bellman-Ford | $O(V \cdot E)$ | $O(V)$ | Shortest path, negative weights allowed |
| Floyd-Warshall | $O(V^3)$ | $O(V^2)$ | All-pairs shortest path |
| Prim's (binary heap) | $O(E \log V)$ | $O(V)$ | Minimum spanning tree |
| Kruskal's | $O(E \log E)$ | $O(V)$ | Minimum spanning tree |
| Topological sort | $O(V + E)$ | $O(V)$ | DAG ordering, dependency resolution |
| Union-Find (path compression + rank) | $O(\alpha(n))$* | $O(n)$ | Disjoint sets, dynamic connectivity |

$V$ = vertices, $E$ = edges, $\alpha$ = inverse Ackermann function ($\alpha(n) \leq 4$ for all practical $n$).

**Adjacency representation matters:**

| Representation | Space | Check if edge $(u, v)$ exists | Iterate neighbours of $v$ |
|----------------|-------|-------------------------------|---------------------------|
| Adjacency matrix | $O(V^2)$ | $O(1)$ | $O(V)$ |
| Adjacency list | $O(V + E)$ | $O(\deg(v))$ | $O(\deg(v))$ |

For sparse graphs ($E \ll V^2$), adjacency lists save both time and memory. Adjacency matrices pay off only for dense graphs or when $O(1)$ edge existence queries dominate.

## Tricky Cases and Gotchas

### 1. String concatenation inside a loop

Where strings are immutable, appending in a loop copies the entire growing prefix on every step: $L + 2L + \cdots + nL = O(n^2 L)$.

```python
# O(n²) — each += allocates and copies a longer string
result = ""
for part in parts:
    result += part

# O(n) — one allocation, one copy per part
result = "".join(parts)
```
```julia
# O(n²) — each *= allocates and copies a longer string
result = ""
for part in parts
    result *= part
end

# O(n) — one allocation, one copy per part
result = join(parts)
```
```ts
// Engines like V8 often build a "rope" for += instead of copying,
// but the spec doesn't guarantee it
let result = "";
for (const part of parts) {
  result += part;
}

// O(n) — the portable choice
const joined = parts.join("");
```
```rust
// O(n²) — format! allocates a brand-new String every time
let mut result = String::new();
for part in &parts {
    result = format!("{result}{part}");
}

// O(n) amortised — String is a growable buffer, push_str appends in place
let mut result = String::new();
for part in &parts {
    result.push_str(part);
}
```

### 2. Slicing inside a loop

In Python, Julia (`arr[i:end]`), and TypeScript (`arr.slice(i)`), slicing **copies** the subarray — turning a single loop into $n + (n-1) + \cdots + 1 = O(n^2)$:

```python
for i in range(n):
    process(arr[i:])    # slice copies O(n - i) elements → O(n²) total
```
```julia
for i in 1:n
    process(arr[i:end])          # copies O(n - i) elements → O(n²) total
    # process(@view arr[i:end])  # a view is O(1) — no copy
end
```
```ts
for (let i = 0; i < n; i++) {
  process(arr.slice(i));   // copies O(n - i) elements → O(n²) total
}
```
```rust
for i in 0..n {
    process(arr[i..].to_vec());   // .to_vec() copies O(n - i) elements → O(n²) total
    // process(&arr[i..]);        // a borrowed slice is O(1) — no copy
}
```

Pass start/end indices instead of copying slices, or use a zero-copy view (`@view` in Julia, `&arr[i..]` in Rust).

### 3. Constants matter on small or nearly-sorted inputs

Insertion sort is $O(n^2)$ and merge sort is $O(n \log n)$, yet insertion sort beats merge sort on a 20-element or nearly-sorted array because it avoids recursion overhead and extra allocations. Big O ignores constants — knowing when constants win is part of the craft.

### 4. Hash table worst case

Hash lookups are $O(1)$ **average**, not $O(1)$ worst case. If all keys collide into one bucket, lookups degrade to $O(n)$. Modern runtimes (Python's randomised hash seed, Rust's keyed SipHash) defend against adversarial strings, but custom hash functions can still accidentally create collisions.

### 5. Already-sorted input changes sorting behaviour

| Algorithm | On already-sorted input |
|-----------|------------------------|
| Insertion sort | $O(n)$ — best case |
| Timsort (Python) | $O(n)$ — detects existing runs |
| Merge sort | $O(n \log n)$ — unchanged |
| Quick sort (naive pivot) | $O(n^2)$ — worst case |

## Quick Check

Try each question before opening the answer. For a full set of interview drills and a step-by-step interview checklist, continue to [Time Complexity Interview Questions](../time_complexity_interview_questions/).

**Q1.** What are the time and space complexities of this function?

```python
def f(arr):
    result = []
    for i in range(len(arr)):
        for j in range(i, len(arr)):
            result.append(arr[i] + arr[j])
    return result
```
```julia
function f(arr)
    result = eltype(arr)[]
    for i in 1:length(arr)
        for j in i:length(arr)
            push!(result, arr[i] + arr[j])
        end
    end
    return result
end
```
```ts
function f(arr: number[]): number[] {
  const result: number[] = [];
  for (let i = 0; i < arr.length; i++) {
    for (let j = i; j < arr.length; j++) {
      result.push(arr[i] + arr[j]);
    }
  }
  return result;
}
```
```rust
fn f(arr: &[i32]) -> Vec<i32> {
    let mut result = Vec::new();
    for i in 0..arr.len() {
        for j in i..arr.len() {
            result.push(arr[i] + arr[j]);
        }
    }
    result
}
```

<details>
<summary>Show answer</summary>

$O(n^2)$ time and $O(n^2)$ space. The inner loop runs $n + (n-1) + \cdots + 1 = \frac{n(n+1)}{2} = O(n^2)$ times, and every iteration appends an entry to `result`.

</details>

**Q2.** Why is `list.pop(0)` $O(n)$ while `list.pop()` is $O(1)$?

<details>
<summary>Show answer</summary>

A dynamic array stores items contiguously. Removing from the end only decrements the length ($O(1)$). Removing from index 0 requires shifting all $n - 1$ remaining elements left by one slot ($O(n)$). Use a deque if you need $O(1)$ removal from both ends.

</details>

**Q3.** What is the time complexity of building a hash set from an array of $n$ elements, then running $q$ membership queries?

<details>
<summary>Show answer</summary>

$O(n + q)$ average time ($O(n)$ to build the set, $O(1)$ per query) and $O(n)$ extra space. Note that $n$ and $q$ are independent variables, so both stay in the bound.

</details>

**Q4.** Two algorithms both run in $O(n \log n)$. Can you tell from Big O alone which is faster?

<details>
<summary>Show answer</summary>

No. Big O hides constant factors, memory allocations, and cache locality. One algorithm could do $2\,n\log n$ operations in-place while another does $50\,n\log n$ with heavy heap allocations.

</details>

**Q5.** How would you optimize an $O(n^2)$ double loop that checks whether an array contains any duplicate?

<details>
<summary>Show answer</summary>

Track seen elements in a hash set (`O(n)` time, `O(n)` space), returning early on the first repeat. If you cannot use extra space, sort in-place (`O(n log n)` time) and check adjacent elements.

</details>
